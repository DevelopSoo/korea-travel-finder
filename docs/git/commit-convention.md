# Git 규칙 (커밋 · 브랜치 · PR)

## 1. 커밋 메시지

### 형식

```
타입: 한국어 요약

(선택) 본문 — 무엇을 왜 바꿨는지

Co-Authored-By: ...
```

- 요약은 **한국어**, 50자 이내, 끝에 마침표를 찍지 않는다.
- 요약은 "~ 추가", "~ 수정", "~ 제거"처럼 명사형으로 끝낸다.
- 본문은 요약만으로 이유가 드러나지 않을 때만 쓴다. "어떻게"보다 "왜"를 적는다.
- 요약과 본문 사이는 한 줄 비운다.

### 타입

| 타입 | 언제 쓰나 | 예시 |
| --- | --- | --- |
| `feat` | 새 기능 | `feat: 여행지 검색 필터 추가` |
| `fix` | 버그 수정 | `fix: 지역 선택 시 목록이 비는 문제 수정` |
| `design` | UI·스타일 변경 (동작은 그대로) | `design: 카드 간격을 토큰 값으로 통일` |
| `refactor` | 동작 변화 없는 코드 정리 | `refactor: 검색 로직을 훅으로 분리` |
| `docs` | 문서 | `docs: 커밋 규칙 문서 추가` |
| `chore` | 설정·패키지·빌드 | `chore: eslint 규칙 업데이트` |
| `test` | 테스트 추가·수정 | `test: 검색 필터 단위 테스트 추가` |

### 커밋 단위

- 한 커밋에는 한 가지 목적만 담는다. 기능 추가와 관계없는 리팩터링이 섞였다면 커밋을 나눈다.
- `.env`, `.env.local`, 인증 키, 대용량 빌드 산출물은 커밋하지 않는다.
- 파일은 `git add -A` 대신 **파일 이름을 직접 지정**해 스테이징한다.

## 2. 브랜치

### 이름

```
타입/짧은-영어-설명
```

- 타입은 커밋 타입과 같은 목록을 쓴다.
- 설명은 영어 소문자와 하이픈(`-`)만 쓰고 2~4단어로 짧게 쓴다.
- 예: `feat/search-filter`, `fix/empty-region-list`, `docs/git-convention`

### 운영

- `main`에서 바로 작업하지 않는다. 작업을 시작할 때 `main`에서 새 브랜치를 만든다.
- 한 브랜치에는 한 작업만 담는다.

## 3. PR (Pull Request)

### 제목

커밋 요약과 같은 형식(`타입: 한국어 요약`)으로 쓴다.

### 본문 템플릿

```markdown
## 변경 사항
- 무엇을 바꿨는지 불릿으로

## 이유
- 왜 바꿨는지 (관련 기획 문서가 있으면 경로 명시)

## 확인 방법
- [ ] 확인 절차 (예: `npm run build` 통과, 특정 화면에서 동작 확인)
```

### 운영

- PR은 `gh pr create`로 만들고, 대상 브랜치는 `main`이다.
- PR을 만들기 전에 `npm run lint`와 `npm run build`가 통과하는지 확인한다.

## 4. 금지 사항

- 사용자가 요청하지 않은 push와 PR 생성
- `main` 브랜치에 바로 push
- 강제 push(`git push --force`)
- `--no-verify` 등으로 hook을 건너뛰기
- 이미 push한 커밋을 `commit --amend`나 rebase로 고치기
